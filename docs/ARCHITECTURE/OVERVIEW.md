# Архитектурный обзор

- **Статус:** предварительные целевые границы; это не описание существующего кода.
- **Цель:** отделить модель времени, Android-интеграцию, UI и необязательную интеллектуальную настройку.

## Предварительные логические слои

### 1. Domain / модель времени

Платформенно-независимые сущности и правила: будильник, повтор, исключение, таймер, состояние таймера, последовательный/параллельный сценарий, временная зона, конфликт расписания и валидация.

Окончательные сущности и схема не определены. Их следует согласовать с моделью AOSP, если проект решит наследовать её.

### 2. Application / операции

Типизированные действия над моделью: создать или изменить будильник, сохранить пресет таймера, изменить шаг сценария, проверить конфликт, получить предварительный просмотр, применить или отменить изменение.

UI и ИИ должны использовать одинаковую семантику операций. ИИ не должен обходить валидацию или писать в хранилище напрямую.

### 3. Android platform integration

Адаптеры для AlarmManager, уведомлений, аудиосистемы, системных событий, перезагрузки и сохранённых данных. Конкретные APIs и ограничения необходимо установить после исследования целевых Android-версий.

### 4. UI / UX

Базовые экраны, расширенное редактирование, шаблоны, сценарии и preview изменений. Основные действия доступны без AI-интерфейса.

### 5. AI provider adapters (optional)

Адаптеры провайдеров преобразуют запрос пользователя в предложения структурированных операций, сообщают о неоднозначности и объясняют результат. Валидация и исполнение остаются ответственностью приложения.

## Архитектурные принципы

- local-first для уже созданных расписаний;
- явные границы между моделью, UI и платформенными API;
- валидация до записи состояния;
- миграции данных по объявленной политике;
- минимальные разрешения;
- минимизация персональных данных в логах;
- тестируемость правил времени независимо от UI.

После изучения upstream нужно определить, какие части уже реализованы в AOSP и где адаптация лучше новой реализации. Не следует проектировать дублирующие подсистемы без необходимости.
