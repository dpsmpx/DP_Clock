# Стратегия качества и тестирования

- **Статус:** план. Есть unit-тесты на JVM — правила времени в `:core:model` (переходы на летнее и зимнее время, пояса, високосный год, дата, пропуск, сменные графики, исключения, шаблоны, цепочки таймеров, перезагрузка, секундомер), производственный календарь — сверка с официальными данными 2026–2027 годов, задачи и снимок места для подтверждения пробуждения, распознавание QR-кода, время ложиться и рассвет, оформление — контраст текста ≥ 4,5 на схемах из 19 цветов, на высоком контрасте — ≥ 7 и границы ≥ 4,5 (0.11.0), чистый чёрный, круг цвета, сегменты табло, оттенок и шов круга шума; статистика — подъём по первому «Выключить» утром, отложенное до него, средние в будни и выходные, сон от самого позднего «лёг» (днём и ночью после подъёма — не в счёт), таймеры по названию, опоздания и пропуски, период; календарь телефона — даты исключений из событий на весь день и длиннее суток, подъёмы перед ранними событиями (раньше обычного будильника, выходной, прошедший подъём), ближайшее событие и события дня; команды ассистента — дни `Calendar`, повторное использование такого же будильника, длина таймера; деление вверх без API 35; мировые часы — день и ночь по солнцу (полярный день и ночь, восход в Москве с точностью до нескольких минут), разница поясов с летним временем, — погода: коды MET Norway, разбор настоящего ответа, правило «не чаще раза в час и не раньше Expires», кэш; файл переноса — JSON, полный круг записи и чтения, значения по умолчанию, отказ на чужих и повреждённых файлах, новые id при загрузке, звуки DP_Clock и миграции базы со встроенным SQLite (0.2.0) — и Lint, а для `:core:model` — сверка вызовов Java с API Android 12 (`tools/check-core-api.py`, D-020) — [сборка](../DEVELOPMENT/BUILD.md). Проверок на устройстве ещё нет.
- **Главный риск:** пропущенное или некорректное срабатывание времени.

## 1. Unit-тесты модели времени
Проверять вычисление следующего срабатывания, повторы и исключения, конфликты, состояния таймеров, сериализацию, восстановление, временные зоны и DST. Граничные даты должны быть воспроизводимыми. Модель и правила — [DATA_MODEL.md](../ARCHITECTURE/DATA_MODEL.md); тесты — в модуле `:core:model` на JVM, миграции базы — на JVM со встроенным SQLite (D-009).

## 2. Интеграционные тесты Android
Проверять планирование/отмену событий, перезагрузку, разрешения и их отзыв, уведомления, обновления, миграции, изменение системного времени и временной зоны. Набор тестов должен соответствовать целевым Android-версиям.

## 3. UI-тесты
Основные потоки: создать/изменить/отключить/удалить будильник; создать одноразовый и повторяющийся таймер; сохранить и повторно применить шаблон; исправить конфликт; просмотреть и отменить предложенные ИИ изменения.

## 4. Приёмка на устройствах
Для каждого сценария указывать устройство, прошивку, Android, разрешения и шаги. Проверять фактическое срабатывание для всех сценариев, поддержку которых заявляет проект. План для будильников, таймеров и секундомера — [DEVICE_TEST_PLAN.md](DEVICE_TEST_PLAN.md).

## Критерии качества
- критические сценарии проходят повторяемые проверки;
- нет регрессий в базовых операциях будильника;
- состояние корректно восстанавливается;
- при отсутствии разрешений пользователь получает понятное сообщение;
- критические дефекты на заявленной матрице устройств отсутствуют.

Для релизных тестов фиксировать commit/build, устройство и Android, условия, ожидаемый и фактический результат, логи и ограничения. Пороговые показатели задаются после получения базовых данных.
